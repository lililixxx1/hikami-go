## 二、根因分析

### 2.1 A 类:主播侧推流不稳定(B 站 CDN 返回 404)

**证据链**(以 `live_20260722_220341` 为例,22:03–22:06):

```
22:03:46  ffmpeg record started   stream_url=...live_lh9cht_SSyvkyE_wnrlb.flv  ← 拿到流,开始录
22:03:50  cdn transient error     error="open live stream: http status 404"   budget=4 backoff=2s
22:05:00  stream ended cleanly while still live, attempting reconnect          ← 流"干净结束"但房间仍 live
22:05:14  cdn transient error     budget=3 backoff=4s
22:05:21  cdn transient error     budget=2 backoff=8s
22:05:32  cdn transient error     budget=1 backoff=16s
22:05:51  cdn transient error     budget=0 backoff=32s                         ← 预算耗尽
22:06:24  ffmpeg record started   (最后一次尝试,换 CDN 节点)
22:06:44+ live check: startWithInfo failed  error="channel is already recording" ← 卡住
```

**调用路径与代码位置**:

```
scheduler 每 30s CheckLive(live=true)
  → manager.Start → CreateLive + Enqueue
    → worker.HandleTask → selectStream → recordAudio
      └─ ffmpeg.go:138  返回 "open live stream: http status %d"
         (response.StatusCode 非 2xx,这里是 404)
    → 流提前结束 → manager.go:1017 "stream ended cleanly while still live"
    → 异常 #2 分支 manager.go:783  isCDNTransientError(err) == true
       ├─ cdnRetryBudget 初始=5 (manager.go:762),每轮 -1
       ├─ cdnBackoff 指数退避:2s,4s,8s,16s,32s (manager.go:1075)
       └─ 每轮重试调 selectStream 重新取流 URL
    → 预算耗尽(budget=0)→ break reconnect → 场次 failed
```

**核心判定**:
1. 房间状态 `live=true`(B 站 `getInfoByRoom` 仍报在播),但实际推流已断/未稳定 → 拿到的流 URL 几秒后即被 CDN 回收 → 404。
2. 系统侧的 5 次 CDN 重连 + 指数退避(`isCDNTransientError` / `cdnRetryBudget`,`internal/live_record/manager.go:762,783-815`)已**正确触发**并按设计耗尽,行为符合[异常 #2 修复](./录播稳定性-修复计划.md)的预期。
3. 时间分布(19:40→19:45→20:05→22:03→22:14 间隔极近)+ "几秒内干净结束"的特征,是**主播反复上下播或切流调试设备**的典型表现。同一 `stream_url` 路径在不同 `live_bvc/{cid}/` 下频繁更换(`SSyvkyE`→`SDk5rFI`→`SorEM2c`…),对应主播每次重开生成的新流。

> **结论**:A 类是 B 站侧推流不稳定导致的外部失败,非系统 bug。系统的重连机制已尽力,但主播下一秒又重开新流,旧流 URL 无法接续。

### 2.2 B 类:ASR 音频时长过短被 dashscope 判 FAILED

**证据链**:

| 场次 | 录制结果 | mp3 时长 | mp3 大小 | dashscope task | 状态变迁 |
|------|----------|----------|----------|----------------|----------|
| `live_20260722_192938` | ✅ 成功 | **53.5 秒** | 428 KB | `c2b0a540-...` | 提交→RUNNING→**FAILED**(约 10s) |
| `live_20260722_200542` | ✅ 成功 | **44.7 秒** | 358 KB | `d90c08c3-...` | 提交→RUNNING→**FAILED**(约 10s) |

两场均 < 60 秒,是 A 类断流的延伸——主播闪现开播一两分钟就下播,录制只抓到几十秒有效片段。

**代码位置**:`internal/asr/dashscope.go:339-340`

```go
if status == "FAILED" || status == "CANCELED" || status == "CANCELLED" {
    return raw, "", fmt.Errorf("dashscope task %s ended with status %s", taskID, status)
}
```

`dashScopeTaskStatus`(dashscope.go:360)只解析 `output.task_status`;FAILED 时返回的错误**未携带 dashscope 响应体里的 `message`/`errors` 字段**,所以 `task.error` 仅记录到 `"ended with status FAILED"`,无法区分是"时长不足""内容审核""配额超限"还是"音频格式问题"。

> **结论**:B 类根因是音频过短(<60s)导致 dashscope `fun-asr` 判定失败;叠加错误信息记录不全,难以从日志直接确认具体原因(但时长数据强烈指向此)。

### 2.3 根因汇总

| 分类 | 根因 | 归属 | 是否代码缺陷 |
|------|------|------|--------------|
| A 流断(6 场) | 主播侧推流不稳定,B 站 CDN 在流失效后返回 404 | 外部 | 否(重连机制正常工作) |
| B ASR FAILED(2 场) | 音频时长过短(<60s)被 dashscope 拒绝 | 外部(内容)+ 内部(观测不足) | 部分(错误日志不全) |

## 三、影响评估

### 3.1 业务影响

- **直接损失**:8 个场次无回顾产出。其中 A 类 6 场无任何音频产物(流没接上),B 类 2 场有音频但因 ASR 失败未生成回顾。
- **下游阻塞**:因 `auto_asr=1` + `auto_recap=1`,ASR 失败的场次卡在 `failed`,不会自动进回顾/发布环节。
- **可恢复性**:B 类 2 场音频仍在磁盘(`data/.../asr/audio.asr.mp3`),理论上可手动重试 ASR(若 dashscope 接受短音频,或拼接/补白后重提)。A 类 6 场**不可恢复**(原始流已不存在)。
- **波及范围**:仅限该频道当天。其他日期/频道未受影响(本机仅此一个 auto 频道)。

### 3.2 系统健康度

- 服务进程(PID 879)自 7/15 起持续运行,未崩溃、未重启,`Restart=on-failure` 未触发。
- scheduler 30s tick 全程正常(`live check completed` 持续输出)。
- 录制重连机制(异常 #1/#2 修复)按设计工作,退避时序正确。
- **无资源泄漏迹象**:ffmpeg 进程正常启停,无僵尸进程堆积。

### 3.3 噪声影响

- 8 个 `failed` 场次会留在管理界面的回顾列表里,`last_error` 显示为英文技术信息,对非技术用户不友好。
- 22:06–22:15 期间大量 `live check: startWithInfo failed ... "channel is already recording"` WARN 日志(因旧场次卡在 recording 态未清理,scheduler 反复尝试启动被拒),属正常防护但日志偏吵。

## 五、推荐修复方案

> **重要前提**:A 类 6 场是外部因素、不可恢复、非代码缺陷,**不需要也无法通过改代码修复**。B 类 2 场音频在手,可手动处置。以下方案按优先级排序,均为**面向未来**的增强,不是对昨天的补救。

### 方案 1(高优先级):丰富 ASR FAILED 的错误日志

**问题**:`dashscope.go:340` 返回的 error 只有状态字符串,丢失了 dashscope 响应体里的失败原因。

**改动**(小,低风险):

```go
// internal/asr/dashscope.go:339-341
if status == "FAILED" || status == "CANCELED" || status == "CANCELLED" {
    // 新增:提取 dashscope 返回的 message / errors,便于区分时长/审核/配额/格式
    detail := dashScopeFailureDetail(raw) // 新辅助函数,读 output.message 或 errors
    return raw, "", fmt.Errorf("dashscope task %s ended with status %s: %s", taskID, status, detail)
}
```

新增 `dashScopeFailureDetail(raw)`:优先 `output.message`,其次 `output.errors`,兜底 `"unknown reason"`。

**收益**:下次 ASR FAILED 可直接从 `task.error` 看到具体原因,无需猜测;也为方案 3 的判定提供依据。

**测试**:在 `dashscope_test.go` 加表驱动用例(mock 返回 FAILED + 各种 message 结构),断言 error 字符串包含期望详情。

### 方案 2(中优先级):录制最小时长阈值,跳过短片段的 ASR

**问题**:几十秒的闪现直播无法产出有意义的回顾,却仍提交 dashscope,既消耗配额又制造 failed 记录。

**改动**:

1. 在 ASR 提交前(`internal/worker` 或 `internal/asr` 入口)用 ffprobe 探测时长(已在 normalize 环节有 ffprobe 调用,可复用)。
2. 引入配置项 `asr.min_duration_seconds`(默认 60,0=禁用),低于阈值的场次:
   - 不提交 ASR;
   - 场次标记为 `skipped`(或复用现有非 failed 终态)而非 `failed`,`last_error` 写明"录制时长 Xs 低于阈值 Ys,跳过 ASR"。
3. 前端回顾列表对 `skipped` 态显示中性样式,不与真正的失败混淆。

**收益**:减少无谓的 dashscope 调用与 failed 噪声;管理界面更清晰。

**风险/注意**:
- 需新增场次状态或复用现有状态,要核对状态机(`internal/state`)的转移合法性。
- 阈值应可配,避免误伤合法的短直播(如某些整点报时类)。

### 方案 3(低优先级):清理"已不 recording 但状态卡住"的场次

**问题**:22:06–22:15 出现大量 `startWithInfo failed ... "channel is already recording"` WARN,源于旧场次状态未及时清理。

**改动**:排查 `manager.go` 的 `activeFor` / 状态清理路径,确认流断失败后是否正确将频道从 `recording` 集合移除。若确认是异常 #9 之外的独立小问题,单独建计划。

**收益**:降低 scheduler 日志噪声,避免因状态卡住导致新直播无法启动。

> 注:今天 19:04 场次能正常启动,说明该卡住是暂态(后续 tick 自愈了),优先级不高。

### 方案 4(运维,无需改代码):清理昨天的失败记录

8 个 failed 场次留在列表里是噪声。可:
- 前端逐个删除(若有删除入口);
- 或 DB 直接清理(注意外键约束,建议走 API 而非直接删表):
  ```bash
  # 仅示例,执行前确认 sessions/tasks 的级联关系
  sqlite3 hikami.db "DELETE FROM tasks WHERE session_id IN (...); DELETE FROM sessions WHERE id IN (...);"
  ```
B 类 2 场如想保留音频,先备份 `data/.../asr/audio.asr.mp3` 再删记录。

## 六、结论

昨天 8 场录播失败的**直接根因是主播侧推流不稳定**(反复上下播导致 B 站 CDN 流频繁失效),叠加其中 2 场音频过短触发 dashscope ASR 失败。**两者都不是系统代码 bug**——录制重连机制(异常 #2)按设计正确触发并耗尽,服务全程未异常。

推荐落地的是**面向未来的增强**:方案 1(ASR 错误日志)小而值得做,能显著提升后续 FAILED 的可诊断性;方案 2(最小时长过滤)能减少噪声与配额浪费,中等收益;方案 3/4 属清理性质,可按需。

本分析不包含对昨天失败场次的任何代码补救(A 类不可恢复,B 类音频已存盘可手动处理)。
