# 录播故障排查手册

> 目的:沉淀 2026-07 以来历次录播故障的排查方法、日志语义与救场操作,下次「昨天的直播为什么没录上/没发出来」时直接按图索骥。
> 维护约定:每次新事故定位后,在 §三 档案加一条、§二 对照表补新日志文案;根因翻案要改写原条目而不是叠加。
> 事件级完整细节见各 dated 分析文档(`docs/2026-*` 与 `plans/plan-*`),本手册是索引与操作层。
> 创建:2026-08-21(基于 7-22 ~ 8-20 共 8 起事故的复盘)

## 一、排查总入口:三层定位法(5 分钟分诊)

**永远按 DB → 日志 → 代码 的顺序交叉验证,单看任何一层都会误判(8-20「泄漏」误判的教训)。**

### 第 1 步:查 DB 定状态(哪些场、什么状态、什么错)

```bash
# 昨天所有场次与终态
sqlite3 hikami.db "SELECT id,status,started_at,ended_at,last_error FROM sessions
  WHERE source_type='live_record' AND started_at >= datetime('now','-2 days') ORDER BY started_at;"

# 对应任务链(live_record 之后应有 normalize/asr/recap/publish)
sqlite3 hikami.db "SELECT type,status,attempt,started_at,finished_at,substr(COALESCE(error,''),1,80)
  FROM tasks WHERE session_id='<SESSION_ID>' ORDER BY created_at;"

# 卡在非终态的(录制中超过主播实际直播时长即异常)
sqlite3 hikami.db "SELECT id,status,started_at FROM sessions
  WHERE source_type='live_record' AND status IN ('discovered','recording') AND started_at < datetime('now','-6 hours');"
```

⚠️ **tasks 的 started_at/finished_at/updated_at 会被重试覆盖**(MarkRunning/MarkFailed 重写)——它们是「最后一次尝试」的时间,不是「第一次失败」的时间。要还原历史时序只能靠 journalctl。

### 第 2 步:查 journalctl 定时序(事件发生的真实顺序)

```bash
journalctl -u hikami --since "2026-08-20 20:20" --until "2026-08-20 20:25" --no-pager   # 精确窗口
journalctl -u hikami --since "..." --no-pager | grep -E "record|404|cdn|reconnect|rerecord"  # 按关键词
journalctl -u hikami --since "..." --no-pager | grep -vE "scheduler: running|live check completed"  # 去调度噪声
journalctl -u hikami -f   # 实时跟踪
```

关键判读点:
- **错拍的 `bilibili live status checked`**(非 :29/:59 调度节拍)= 人/UI 触发的探测,不是系统行为。
- 调度器每 30s 一轮 `live check`;`live:true` 持续但无新场次创建 = 有东西挡住建场(看 §二 槽位类日志)。

### 第 3 步:对代码定根因(符号锚定,行号会漂移)

| 关注点 | 入口符号 |
|--------|---------|
| 录制主循环/重连预算/CDN 退避 | `internal/live_record/manager.go`: `HandleTask` / `finishWithAudioIfAny` / `isCDNTransientError` / `cdnBackoff` |
| 同场重录(槽位复活) | `manager.go`: `tryRerecordFailedSlot` / `evaluateRerecordGate` / `hasResidualAudio` |
| 建场与槽位唯一约束 | `internal/session/session.go`: `CreateLive` / `LiveSlotSessionID`(槽键=B站 live_start_time,秒粒度) |
| 拉流与超时 | `internal/live_record/ffmpeg.go`: `openStream`(默认 transport 只限建连/响应头) |
| 任务生命周期/重试前置 | `internal/worker/task.go`: `Retry`(WHERE status='failed')/ `MarkRunning` / `MarkFailed` |
| 崩溃恢复 | `internal/worker/worker.go`: `recoverRunning`(live_record 按进程存活判定) |
| 状态机 | `internal/state/state.go`(`failed→live_record_started→recording` 合法,M6) |

### 快速分诊表(症状 → 直接跳)

| 症状 | 大概率类别 |
|------|-----------|
| 场次 failed,raw/ 无任何 audio.* | 闪断型失败(§三.1);8-21 起应自动复活重录,没复活看 §二 槽位日志 |
| 场次 failed,raw/ 有非空 audio.part.* | 音频保全场景(§三.2 / §四.1 人工救场) |
| 场次卡 recording 数小时,主播早下播 | 挂起型(§三.5)或槽位占用假象(§三.6) |
| 录制成功但无回顾文档 | 下游故障:asr(§三.4)/ recap(§三.3)/ 回放类不自动发布(§四.2) |
| 「already recording」风暴 | 槽位冲突(§三.6),8-21 起日志已诚实化 |

## 二、日志文案对照表(先看这里再下结论)

| 日志 msg | 真实含义 | 下一步 |
|----------|---------|--------|
| `ffmpeg record started` | ffmpeg **即将尝试**拉流——打在 openStream **之前**,不代表进程真起来了(404 时进程从未启动) | 继续看后续是否有 `cdn transient error` |
| `cdn transient error, retrying with backoff` | 拉流 404/reset,CDN 预算 -1 指数退避(2/4/8/16/32s) | 正常重试,无需处理 |
| `reconnect budget exhausted with no valid audio, finishing with error` | 预算耗尽且**零音频**,按失败收尾——**正确行为** | 8-21 起等冷却自动复活;看后续 `rerecord scheduled` |
| `reconnect budget exhausted, finishing with recorded audio preserved` | 预算耗尽但有已录音频,按**成功**收尾送流水线 | 无需处理 |
| `channel is already recording`(每 30s 重复) | **不一定是真在录!** 8-21 前该文案同时覆盖三种来源:内存 active / DB 活跃场 / **槽位唯一约束冲突** | 8-21 起看同 tick 的伴随日志(下列 5 条)定来源 |
| `live slot failed recently, waiting re-record cooldown` | 槽内场已 failed,等冷却(默认 600s)后自动复活 | 无需处理 |
| `rerecord scheduled for failed live slot session` | 冷却已到,已自动 Retry 槽内失败场次的录制任务 | 确认后续正常走 `live record started` |
| `live slot has residual recorded audio, auto re-record disabled to protect it` | 失败场残留**有效音频**,自动复活被禁(防 -y 截断销毁) | **需人工**:§四.1 救音频,或确认后手动重试任务 |
| `live slot re-record attempts exhausted` | 同场重试达上限(默认 3) | **需人工**:§四.4 删除失败场释放槽位 |
| `live slot failed but live_record task unavailable (task_status=missing/cancelled)` | 死槽:场 failed 但任务被删/取消 | **需人工**:§四.4 |
| `re-record already scheduled` | 复活已调度(任务 pending/running),幂等跳过 | 无需处理 |
| `preflight live check reports offline, skip recording` | 任务启动时主播已下播,干净快速失败(常见于手动重试过期任务) | 无需处理 |
| `task handler returned error after context cancelled` | 任务被主动取消(Stop/Cancel),H3 设计不落终态 | 仅在非人工取消场景关注 |
| `dashscope task ... ended with status FAILED` | DashScope 判失败;短音频(<60s)是主因之一 | 查音频时长;7-22 B 类 |
| `recap provider response missing content` + finish_reason | LLM 返回空正文;`length`=token 预算耗尽(确定性),`stop`+空需看是否 reasoning 挤占 | §三.3 |
| `recap provider returned empty content` 且 `finish_reason:""`、`raw_len:2` | DeepSeek **非流式请求 ~180s 服务端时间墙**:生成超时被服务端掐断,返回空 JSON `{}`(实测逐次精确 180.00s)。提示词越复杂(多人联动/超长转写)思考越久越必撞 | §三.7:`PUT /api/config/recap {"thinking_enabled":false}` 后重试任务 |
| `recap provider returned empty content` + `finish_reason=stop` + reasoning_content 中途断句 | 思考模式推理未完成即被掐(180s 墙或思考预算);stop 不代表正常结束(DeepSeek 行为特性) | 同上,§三.7 |
| `danmaku connection interrupted, reconnecting` | 弹幕 WS 断线重连(与音频录制独立) | 一般无需处理 |

## 三、已解决问题档案(按症状检索)

### 1. 开播闪断 → 整场未录(2026-07-22 多场、2026-08-19)
- **症状**:场次 failed,`open live stream: http status 404`,CDN 预算 5→0 耗尽,raw/ 零音频。
- **根因**:B 站开播瞬间 CDN 未就绪/房间瞬切,全部重试撞 404。失败本身**正确**(外部原因)。
- **真正的 bug(2026-08-21 修复)**:同一场直播(live_start_time 恒定)期间,失败场占住 `(channel, live_record, live-<room>-<live_start_time>)` 唯一约束,每 30s 建场必撞,被误导性映射为 "already recording"——**主播复播的 3h12m 永远无法重录**。
- **修复**:`rerecord_cooldown_seconds`(600,0=禁)/`rerecord_max_attempts`(3);冷却后自动 Retry 槽内失败任务(状态机 failed→recording 已放行)。计划 `plans/plan-liverecord-rerecord-2026-08-20.md`。
- **预防**:无(外部诱因),但损失被限制在冷却窗口(~11 分钟)内;开头段可用 §四.2 官方回放补。

### 2. 录满整场却被判 failed(2026-08-02、2026-08-07)
- **症状**:audio.part.N.m4a 完整(几百 MB),session failed,流水线没跑。
- **根因**:下播瞬间 B 站 live 探测有缓存(live:true 滞后),重连全 404 耗尽;旧代码 4 条耗尽分支中部分无「有音频则成功收尾」守卫。
- **修复(2026-08-08)**:`finishWithAudioIfAny` 统一收口 4 条耗尽分支(有音频→成功保留送 normalize);风控中止/明确判败/主动取消**有意**不走该收口。
- **救场**:§四.1。

### 3. 回顾文档没发出来 —— recap 空 content(2026-08-13,ISSUE-007)
- **症状**:session failed,`recap provider response missing content`,ASR/音频完好。
- **根因**:flash/reasoning 模型 + max_tokens(16384)对 DeepSeek 限制的是 reasoning+completion**总和**,reasoning 爆炸挤空正文;且 DeepSeek 耗尽时常报 `stop` 而非 `length`,finish_reason 不能单独定性。
- **修复**:空 content 兜底重试(`length` 确定性耗尽不重试)+ finish_reason/reasoning 片段诊断日志;运维:pro 模型 + max_tokens 32768。
- **救场**:session UPDATE 回 asr_done + 重置 recap task 为 pending + 重启(§四.3)。

### 4. 崩溃/中断后的恢复类(2026-07-31、2026-08-01、2026-08-16)
- **7-31/8-1**:OOM 后 session 卡 asr_submitted——recoverRunning 只重排不降级状态,重入撞非法转换。修复:恢复时 `syncSessionState` 降级到 failed 再重排。**根因层**:OOM 是开发机残留进程占 4G 内存,清掉即愈——排查时先 `free -m` 看环境。
- **8-16(ISSUE-006)**:崩溃窗口内 ASR 重启会**重复提交 DashScope 付费任务**。修复:dashscope_task_id 持久化进 task payload,恢复重入走 await 轮询零付费;fail-closed 网络错误不静默重提交。
- **原则**:崩溃恢复后凡涉及付费远端操作,先查 payload 里有没有幂等键。

### 5. 挂起型(理论):openStream 无超时
- 原分析怀疑的「20h 泄漏」不存在(见 §三.6),但 openStream 曾回退无超时的 http.DefaultClient——CDN TCP 挂起(非 404 快速失败)会真占用 active 槽。**2026-08-21 已修**:包级 transport(Dial 10s/TLS 10s/ResponseHeaderTimeout 15s),特意不设 Client.Timeout(会掐断数小时长流)。

### 6.5 十人联动 recap 三次全灭 —— DeepSeek 非流式 180s 服务端墙(2026-08-21 场,08-22 定因修复)
- **症状**:录制/normalize/ASR 全部成功(2700 段/103K 字转写),recap 3 次尝试全部空 content:两次 `finish_reason=stop` 且 reasoning_content 中途断句(模型已正确理解「十人联动」任务),一次恰 180.00s 返回 `{}`;调大 max_tokens 32768→65536 后反而三次全部精确 180s 撞墙返回 `{}`。
- **根因**:DeepSeek V4 系模型默认思考模式(reasoning_effort=high),**非流式请求生成超 ~180s 会被服务端掐断**(官方文档证实非流式仅发空行保活,长生成推荐流式)。十人联动 3.5h 的提示词达 **51,950 prompt tokens**(usage 实测),high 档思考必然超墙;调大 max_tokens 只让思考更久,必撞。ISSUE-007(8-13)是同族但不同层:那次是 max_tokens 预算耗尽,这次是时间墙,二者 DeepSeek 都常报 `stop` 而非 `length`/超时错。
- **修复(2026-08-22)**:recap_ai 新增 `thinking_enabled`(false=发 `thinking:{"type":"disabled"}` 跳过思考直接作答)与 `reasoning_effort`(low/high/max…)两配置,缺省不发送(零回归)。回顾任务是固定结构模板提示词,不依赖深度思考;关闭后 completion 仅 3,226 tokens、约 2 分钟一次通过。**当前生产已设 `thinking_enabled=false`**。
- **代价**:非思考模式对超复杂内容的组织力略弱于 high 档思考;若后续场次质量下降,可改 `reasoning_effort:low`(保留轻思考)并接受部分场次可能仍撞墙,或等待流式请求支持。

### 7. 误判档案:「20 小时 active 泄漏」(2026-08-20 → 08-21 翻案)
- **原误判**:以为任务 20:21:52 后未返回、active 泄漏 20h、attempt=2 异常。
- **真相**:任务 20:21:53 干净完成;「时间戳停在 16:44」是次日手动重试**覆盖**;风暴来自槽位约束(§三.1);attempt=2 就是那次手动重试。
- **三条反证手法**(复用价值高):① run-2 能打出 `live record started` ⇒ setActive 通过 ⇒ active map 为空;② Retry 成功(attempt+1)⇒ 任务此前必为 failed ⇒ 第一次 MarkFailed 执行过;③ 同款 8-09 案例 83 秒干净完成 ⇒ 路径本身无泄漏。
- **教训**:接口语义误导(startWithInfo 把三种来源都映射成 already recording)+ 时间戳覆盖效应。两者分别由 F2 日志诚实化与本手册 §一 的警告项防御。

## 四、运维救场手册

### 1. 残留音频人工救场(failed 场有非空 audio.part.*)
```bash
# 确认残留(任一 Size()>0 即可救)
ls -lh data/<channel>/<slug>/raw/
# 保留 part 备份,取最长段作主文件(走 normalize 首选路径)
cp data/<channel>/<slug>/raw/audio.part.N.m4a data/<channel>/<slug>/raw/audio.m4a
# 插 pending normalize 任务(normalize 不解析 payload,{} 即可)
sqlite3 hikami.db "INSERT INTO tasks(id,channel_id,session_id,type,status,payload,attempt)
  VALUES ('task_manual_<ts>','<channel>','<session>','normalize','pending','{}',1);"
make build-go && systemctl restart hikami   # recoverRunning 重新入队 pending
```
随后 auto_asr/auto_recap 自动续到发布。内存紧张时先 `free -m`。

### 2. 官方回放补档(零音频整场丢失的终极兜底)
1. 拿官方录播 URL(完整 `https://www.bilibili.com/video/BVxxx` 形式)。
2. `POST /api/sessions/download-by-url`,body `{"channel_id":"...","url":"..."}`(X-Admin-Token 鉴权)→ 自动 download→normalize→asr→recap。
3. **注意**:回放类(download)按设计**不自动发布**——手动 `POST /api/sessions/<sid>/publish`。
4. 标题无日期时 started_at 会落到下载时刻:发布前改回顾 md 首行日期 + `UPDATE sessions SET started_at=... WHERE id=...` 回填真实开播时间(发布标题取 md 首行)。

### 3. 卡 failed 的场次/任务处置
- 重试任务:`POST /api/tasks/<id>/retry`,**前置 status=failed**(running/pending 会被拒,ErrTaskConflict)。
- reset API(`ResetFailedSession`)**只接受 ASR 失败**场景(要求 asr/audio.asr.mp3 存在);live_record/normalize 失败走 §四.1/§四.2。
- recap 失败后重跑:canHandleRecap 已接受 failed,直接 retry recap task 即可(2026-08-13 起),无需先改 session 状态;若报错含 `finish_reason=stop` 且响应曾出现 180s/`{}`,先按 §三.6.5 关思考再重试。

### 4. 释放被占的槽位(死槽/次数耗尽)
`DELETE /api/sessions/<sid>`(先删 tasks 再删 session);下一 tick 调度器即可对同场直播重建场次。直接 SQL 亦可,但走 API 保证级联。

## 五、陷阱清单(每次都重新踩过的)

1. **tasks 时间戳被重试覆盖**:不是首次失败时刻(§一 步骤 1)。
2. **`already recording` 语义过载**:8-21 前三种来源一个文案;旧日志分析必须配合槽位约束知识解读。
3. **sqlite 直接改 runtime_settings**:`json_set()` 会把列类型 BLOB→TEXT,导致服务崩溃循环——走 handler API 或 `CAST(... AS BLOB)`。
4. **`make build-go` 不重建前端**:内嵌的是 `cmd/hikami/webdist`,纯 go build 会把陈旧前端嵌进去;改过 web/ 必须 `make web-build` 再编译。
5. **后台进程 kill 打偏**:`cd dir && nohup ./bin &` 后 `$!` 是子 shell 的 pid,kill 打不中真实进程——用 `pgrep -f` 或直接记录真实 pid。
6. **http.Client.Timeout 掐断长流**:流式下载/录制只能限建连与响应头(Transport 层),不能限整请求周期。
7. **`ffmpeg record started` 先于 openStream**:日志出现 ≠ ffmpeg 进程存在。
8. **弹幕采集器独立生命周期**:`go func()` 派生、ctx 取消后 ~30s 内退出(心跳周期),与音频录制互不阻塞;`danmaku.jsonl` 是 O_APPEND,重录段追加不改写旧段。
9. **错误匹配靠字符串**:`isCDNTransientError` 用子串匹配("http status 404"/"connection reset"),改错误文案前先 grep 它。

## 六、当前已知残余风险与验证待办

- **冷却窗口损失**:闪断失败 → 复活约 10 分钟,头部内容丢失(可 §四.2 官方回放补)。
- **残留音频型不自动复活**(有意取舍):见 WARN 后走 §四.1。
- **attempt 耗尽(默认 3)后需人工**释放槽位。
- **思考模式当前开启**(`thinking_enabled=true` + `reasoning_effort=high`,模型 flash,2026-08-22 用户指定、与官方有效档位 low/high/max 对齐):普通场次 8-20 实证思考模式 80s 可过;但十人联动级超复杂场次(52K token 提示词)思考开启仍可能撞 §三.6.5 的 180s 墙——届时按 §四.3 临时 `thinking_enabled=false` 救场,或降档 `low`。根治方向是 recap 请求改流式(`stream:true`,DeepSeek 官方推荐,无时间墙),零件未备。
- **B 站新形态**(风控升级/API 变更)可能出现未见路径——按 §一 三层定位法新起排查。
- **待实测**:下次直播窗口验证同场重录全链路(含残留音频 WARN 路径)。
- **未来方向**:官方回放自动补档链(live 失败后 N 小时检测官方录播自动 download-by-url),现有零件齐全只差编排。
