# 问题分析：2026-08-19 录播失败 — 开播闪断 404 与 20 小时 active 泄漏

> **⚠️ 2026-08-20（晚）复核结论：本文档的根因 B「20 小时 active 泄漏」不成立**，据此撤销 §四 P1 的看门狗等修复方向。经重新取证（journalctl 全窗口 + DB 历史任务表 + 代码逐行复核 + 三轮 general-purpose 审核背书），真相是：
>
> 1. **任务在 20:21:53 就干净完成了**——HandleTask 正常返回、defer 清 active、worker `fail()` 落库 MarkFailed（attempt=1）+ session failed。「tasks 时间戳停在 16:44:07」是次日 16:44:07 用户在 UI 手动重试（run-2）的 MarkRunning/MarkFailed **覆盖**所致，不是「第一次 MarkFailed 从未发生」的证据。16:44 run-2 能通过 setActive（走到 preflight）证明 active map 早已为空；Retry 要求 status=failed 也证明 task 早已 failed。
> 2. **20:22–23:34 的 "channel is already recording" 风暴真凶是开播时间槽唯一约束**：`session.CreateLive` 用 B 站 `live_start_time` 生成 `source_id=live-<room>-<时间戳>` 并落 `(channel, source_type, source_id)` UNIQUE（注释明示含失败态，防下播竞态）。同一场直播（live_start_time 不变）期间，每 30s 调度 tick 建场必撞约束 → `ErrAlreadyLive` 被映射为误导性的 `ErrAlreadyRecording`。**主播 20:22 复播后的 3h12m 真实直播因 failed 场占槽永远无法重录——这才是本次事件的全部损失。** 23:34 下播后风暴自然停止（无 tick 触发，不是「解锁」）。
> 3. §二 根因 B 的各推断逐一被推翻：耗尽 WARN 之后到 return 之间无任何阻塞点（m.mu 临界区全是短 map 操作；Hub.Broadcast buffered+非阻塞）；弹幕采集器 23:35 后仍在连接内（journal 无重连日志），与「下播解锁」无关；hikami-e2e 独立 DB/端口，无并发写。历史交叉验证：7-22 同款风暴在主播 22:15 复播（=新 live_start_time=新槽）瞬间消失；8-09 同款闪断 83 秒干净完成（主播每次闪断重开=新槽）。attempt=2 是用户手动重试。

## 一、现象

- 昨晚 20:20:29 scheduler 检测 `live=true` 建 `live_record` 场次并入队，`task_acecf97256797bfa37279f45e79fd40f`。
- 20:20:30 起 6 次 `ffmpeg record started`（`audio.m4a` + `audio.part.1..5.m4a`），每次 `open live stream` 均 `http status 404`，走 CDN 瞬时错误分支 `cdnRetryBudget=5` 指数退避 2s/4s/8s/16s/32s 耗尽。
- 20:21:52 打 `WARN reconnect budget exhausted with no valid audio, finishing with error scenario=cdn carry_error="open live stream: http status 404"`。
- **预期**：零音频走失败，不送 `normalize`，任务在 20:21:52 标记 `failed` 释放。
- **实测**：任务未在 20:21:52 结束，`activeRecord` 泄漏 20 小时，至次日 16:44:07 才以 `channel is not live`（preflight offline）二次 `live record started` 同一 `session_id` 并落库 `failed attempt=2`。期间 20:22 起每 30s scheduler 报 `live:true` + `channel is already recording`。
- 磁盘：`data/bili_1298779265/live_20260819_202026/raw` 仅 `cover.jpg` / `danmaku.jsonl` / `live.raw.json`，无任何 `audio.*`，弹幕约 77KB。

---

## 二、根因

### 根因 A — B 站开播闪断（触发器，代码处理正确）

- 调度 `CheckLive live=true` 后，`selectStream` 拿到的 `live-bvc/*.flv` URL 在 `openStream` 的 `http.Get` 阶段即 404（CDN 未就绪/房间瞬切）。
- 代码（行号为区间，HEAD 漂移时以符号为准）：`manager.go` `cdnRetryBudget` 定义区（`cdnRetryBudget:=5` / `cdnAttempt:=0`）、独立预算分支（`isCDNTransientError` + `cdnRetryBudget<=0 → finishWithAudioIfAny("cdn",…)` + `break reconnect`）、`cdnBackoff` 指数退避 `2/4/8/16/32s`（`1<<attempt`，`>=6` 封顶 60s）、`isCDNTransientError` 判定 `http status 404 || connection reset || (EOF && "open live stream")`（注意 Go 运算符优先级 `&& > ||`，第三项需同时含 `EOF` 与 `open live stream`）与日志 `5→4→3→2→1→0→exhausted` 一一对应。
- `audioFileExists` 要求 `Size()>0` → `addAudioSegment` 过滤 → `hasRecordedAudio` 判空 → `finishWithAudioIfAny("cdn", …)` 零音频返回 `carryErr` 走失败，符合 2026-08-08 统一收口（`manager.go: finishWithAudioIfAny`）。与 08-02/08-07 的「有音频白录应保留」正确区分。
- `cover.jpg` 来自 `preflight.Cover` 复用，`danmaku.jsonl` 77KB 来自 `recordDanmakuWithStartTime` 独立 goroutine，与音频缺失不矛盾。
- 结论：A 为外部流失效，`failed` 是预期行为，不应调大 `cdnRetryBudget`。

### 根因 B — 20 小时 active 泄漏 + attempt=2 异常重入（软件 bug，需修）

- `20:21:52` 已 `break reconnect`，循环后仅 `peekAbortReason`（锁读）与空 `finalizeAudioSegments`，无阻塞点，却未 `return err` 到 `worker.runTask`。
- `journalctl` 20:21:52 后无 `MarkFailed`/`auto retry`/`stale task` 日志，`tasks.updated_at` 停在次日 `16:44:07` 而非 `20:21:52`，`started_at` 也被覆盖为 `16:44:07`，证第一次 `MarkFailed` 从未发生。
- `activeRecord` 未被 `defer clearActive` 释放，导致 scheduler 20 小时 `already recording` 死锁。
- `attempt=2` 与 `worker.go: nonRetryableTypes[live_record]` + `ShouldAutoRetry` 恒 `false` 矛盾，且 `recoverRunning` 对 `live_record` 仅 `MarkFailed` 不 `ResetToPending`。唯一增 `attempt` 的 `Store.Retry` 需人工 `POST /api/tasks/:id/retry`，与 `16:43:51` 错位节拍的 `live status checked` 时机吻合，指向并发写库/手工重入覆盖（`ps` 显示 `973440 ./hikami-e2e -config config.yaml` 与主 `977251` 同库并发，SQLite 同库双写可能产生 `SQLITE_BUSY`/WAL 竞态覆盖 `tasks.message/attempt`）。
- 阻塞点研判（当前为推断，待 `pprof goroutine` 实证）：日志已打 `exhausted` 证明 `openStream` 已返回 404、`recordAudio` 已结束于 CDN 分支，因此 20h 泄漏点不在 CDN 404 快速失败路径本身；更可能卡在最后一次 `recordAudio` 的 `io.Copy`/`cmd.Wait` 或 `http.DefaultClient`（`FFmpegRecorder.HTTPClient==nil` 时回退无 `Timeout` 的 `http.DefaultClient`，`cmd/hikami/main.go` 未注入）对非 404 的 TCP hang（如 `connection reset` 未返回而 hang）。当前现场为 404 快速失败，hang 未触发，泄漏点仍待实证。
- `Store.Retry` 复用同一 `task.ID` 仅 `attempt+1`，`syncSessionState` 的 `stale` 丢弃以 `attempt` 比对而非 `taskID`（`worker.go: syncSessionState`）。
- 结论：B 为独立 bug，`attempt=2` 为二次重入覆盖，非自动重试。

### 方案 P1 — 修复 20h 泄漏（另起变更，不在本文件范围，不阻塞 P0）

- `FFmpegRecorder.openStream` 的 `http.Client` 加 `10s Timeout` 与 `context.WithTimeout`，`recordAudio` 的 `io.Copy`/`cmd.Wait` 设总超时并打 `WARN`。

- `worker.runTask` 的 `ctx.Err()!=nil return` 吞错分支加 `WARN`，确保 `MarkFailed` 必达。
- 隔离 `hikami-e2e` 同库并发（改 `db_path` 或单实例独占）。
